# gh-96 — Operator-driven analysis in `wgo dash`

**Issue:** https://github.com/dmihalcik-virtru/wgo/issues/96
**Builds on:** [gh-70](gh-70.md) (the live dashboard), [gh-71](gh-71.md)
(efforts), [gh-72](gh-72.md) (agent sessions).

## Summary

`wgo dash` shows ongoing local work. This epic makes it the place where its
operator answers triage and reporting questions directly — by pointing and
dragging, not by writing one-off scripts: which PRs need me, which need a
reviewer nudged, what shipped last week, which tickets disagree with their
PRs. It widens the snapshot to every PR the configured people author or are
asked to review, adds Jira sprint facts and a few derived facts, and replaces
the single toggle filter with tightly coupled dynamic queries, an analysis
table, a scatterplot, a CI grid, PR timelines and a sprint view. Every answer
is reproducible from the CLI and copyable as Markdown.

## Problem

One real week of triage — one developer, about 200 open PRs across about 20
repositories, a two-person team — needed answers the dash could not give, so
each was produced with ad-hoc GraphQL and Python:

| Question | Why the dash cannot answer it today |
|---|---|
| Which of my PRs should I work on, and which should I push onto reviewers? | PRs appear only through a local bookmark (`internal/dash/remote.go:28`), so most open PRs are invisible. PRs lack created date, size, mergeability, failing check names and reviews (`internal/dash/model.go:209`). |
| Which PRs are ready but have no reviewer, or only a whole team? | Requested reviewers are stored, but there is no "whose move" fact and no way to filter on it. |
| Are this PR's failures real, or does that check fail on every PR in the repo? | Only a CI rollup is kept, not per-check results. |
| What shipped last week? | Merged work drops out of `Counts.Activity` (`model.go:295`); merged PRs are not fetched. |
| Which tickets are done but still open in Jira, or in the sprint with no PR? | Tickets carry only status and assignee (`model.go:228`): no sprint, points or resolution, and only tickets reachable from a bookmark. |
| Is review load concentrated on a few people? | No author or reviewer dimension. |
| Any two of the above at once. | One `{by, value}` filter at a time (`internal/review/web/live.js:68`, `:93`); substring search only (`:267`). |
| Put the answer in a weekly update. | No extract beyond `--json`. |

Against Shneiderman's seven tasks: *overview* is partial (local work only),
*zoom* exists (graph), *filter* is a single toggle, *details on demand* are
thin for PRs, *relate* has graph edges but no cross-source mismatches,
*history* is only "since last look", and *extract* is missing.

## Principles

These bind every child spec.

1. **Overview first, zoom and filter, then details on demand** (Shneiderman,
   "The Eyes Have It", 1996). The overview answers "what needs me"; every
   mark leads to its details. Views support the seven tasks where they apply,
   including *history* (browser back/forward) and *extract*.
2. **Dynamic queries** (Ahlberg, Williamson & Shneiderman, CHI '92; Ahlberg &
   Shneiderman, CHI '94 "FilmFinder"):
   - the query is visible: filters are controls that show their own
     distributions, not hidden text;
   - actions are rapid, incremental and reversible: a filter change
     re-renders in under 100 ms at 2,000 nodes, and every change can be
     undone (back) or cleared;
   - selection is by pointing; typing (search, query text) stays available
     but is never required;
   - tight coupling: query output is query input. Each filter shows what the
     other filters leave (Spence & Tweedie's Attribute Explorer), and a
     selection in any view highlights in all of them.
3. **Show the data, not a verdict** (Tufte). Derived facts (gh-99) carry their
   evidence. There is no composite "impact" or "priority" score; ranking is
   the operator's, by sort keys they can see. This is also the repo's
   "Automation Without Opinion" principle.
4. **Data-ink, no chartjunk** (Tufte). No 3-D, gradients, shadows or
   decorative icons; light gridlines; direct labels instead of legends for a
   single series; high data density; small multiples share scales;
   word-sized graphics in tables.
5. **Match the chart to the question** (GWU guide; Tableau). Each view names
   the one question it answers: comparison → bars, distribution → histogram,
   two measures → scatterplot, state across many items → grid, durations →
   timeline, relationships → the existing graph.
6. **Be truthful about scale and data** (GWU "mind the y-axis"; Tufte's lie
   factor). Bars start at zero. Log scales are allowed for sizes and
   durations, are labelled "log scale", and never drive bar length. Unknown
   is never drawn as zero or "none": gh-70's freshness contract extends to
   every new field.
7. **Transparency** (GWU). Every view and extract states its sources, their
   freshness and the active query.
8. **Colour with purpose, accessibly** (GWU; Tableau). Saturated colour is
   reserved for "needs the operator" and for failure; everything else is
   neutral. Colour is never the only encoding: each colour has a redundant
   shape, glyph or text. Palettes are colour-vision-deficiency safe in light
   and dark themes. No rainbow scales.
9. **Exploratory vs explanatory** (GWU). The dash explores; its extracts
   (gh-100) explain — Markdown a person pastes into an update, with links and
   provenance.
10. **Most important first** (Tableau). The top left holds the attention
    summary; the overview has at most three charts besides the filter panel.

Tableau's best-practices page refused automated retrieval (HTTP 403) when this
was written; its points above are its widely published guidance.

## Shared contracts

### Snapshot growth stays additive

Child specs add **optional** JSON fields. An optional addition does not bump
`dash.SchemaVersion`; readers treat a missing field as unknown. A spec bumps
the schema only if it changes an existing field's meaning or type, and must
say so. This keeps parallel branches mergeable.

### Facts carry provenance

Every new remote field records its source and freshness with the existing
`Freshness` (`model.go:31`). A fact derived from unknown inputs is unknown,
never false.

### People

gh-97 introduces `[[dash.people]]` (GitHub login, optional Jira user, display
name). It defaults to the authenticated user plus `[pair]`'s teammate
(`internal/config/config.go:192`, which already has `teammate_jira`). All
person-scoped fetching and the `@me` query macro use it.

### One query language, two runtimes

gh-100 defines a filter grammar shared by the URL hash, `wgo dash --query` and
saved filters, over a field registry defined in Go and served to the page.
The browser (JS) and CLI (Go) evaluators run one shared test-vector file, so
they cannot drift.

### Extension seams in the page

gh-100 exposes registries on `window.WGOLive` for fields, views and overview
panels. Later views ship as separate files under `internal/review/web/`,
inlined through `review.Page.Addons` (`internal/review/web.go:42`), so
parallel work does not collide in `live.js`.

### GET stays side-effect free

gh-70's contract holds: GET routes never run discovery, jj, a process or a
network call. New remote data is fetched by the background `Refresher`
(`internal/dash/remote.go:91`) and by `wgo dash --json --refresh`; the page
only reads.

### Public repository

wgo is public. Specs, fixtures, tests and screenshots use invented data
(`acme/api`, `acme/web`, `alice`, `bob`, `TEAM-123`, a check named
`vendor-hsm-tests`). No real organisation, repository, ticket key, person or
security-fix detail.

### A waited refresh is bounded (delivery note)

Added after a real-data trial (gh-96-real-data-fixes). `wgo dash --json
--refresh` starts lookups for at most `--refresh-timeout` (60 s by default,
`0` for no bound), so it may now return partial data. It says so in its
diagnostics rather than running every job: `not run: refresh deadline
(60s) reached; N lookups left`. Lookups run by priority, the PR inventory
first (the login, then open-authored, review-requested and closed-recent),
because the attention facts depend on it; ticket and issue lookups come
last. Inventory fetches already running at the deadline get up to twice
the timeout again to finish and be cached; one still running then is
cancelled, recorded as such, and explained in `github_inventory`'s detail.
Every other running lookup is cancelled at the deadline (acli is killed,
GitHub requests are abandoned); once its output is written, the command
waits at most a second for them and leaves behind any that has not
stopped, which the atomic cache writes make safe. So it exits within about
three times the timeout. Skipped Jira lookups (acli
logged out), issues GitHub does not find, and lookups left at the deadline
are reported, but only failed lookups make the command exit non-zero.

### Working in parallel

- One jj workspace and bookmark per spec, named `gh-N-<slug>` (listed in each
  spec's `branches:`).
- Land each data spec's **model change first** as its own small PR — gh-97's
  PR fields and fixture, gh-98's ticket and sprint fields, gh-100's registries —
  so dependents can build on fixtures before fetching code lands.
- Conflict hotspots: `internal/dash/model.go` and `internal/dash/assemble.go`
  (gh-97, gh-98, gh-99; append fields, don't reorder), and `live.js` (only gh-100
  restructures it; later specs add addon files and register).
- Each spec's tests pass on main plus its declared dependencies alone.
- Screenshots use the sanitized fixture
  (`internal/dash/testdata/analysis_fixture.json`, introduced by gh-97 and
  extended by later specs) under a sandbox `HOME`.

## Acceptance criteria (epic)

Done when, on the sanitized fixture and on a real `HOME`:

- [ ] Every question in the Problem table is answerable in the browser within
      three pointer actions from a saved filter, without typing.
- [ ] The same answers come from `wgo dash --json --query …` and as Markdown,
      and match the browser.
- [ ] Every child spec's acceptance criteria are checked.
- [ ] No view encodes information by colour alone; each chart passes a
      colour-vision-deficiency simulation (method and result in the PR).
- [ ] Filter changes re-render in under 100 ms at 2,000 nodes on the fixture
      generator (numbers in the PR).

## Out of scope

- Writing to GitHub or Jira from the dash (requesting reviewers, transitions,
  closing PRs). gh-70's token-guarded action API could carry these later.
- A composite impact or priority score.
- Dashboards for people beyond the configured list, or organisation-wide.
- Serving anywhere but loopback.
