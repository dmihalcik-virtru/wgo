# gh-99 — Derived attention facts

**Issue:** https://github.com/dmihalcik-virtru/wgo/issues/99
**Epic:** [gh-96](gh-96.md) · **Wave 2** · Needs gh-97's PR fields; ticket facts
also need gh-98 · Unblocks gh-101, gh-102, gh-103, gh-105

## Summary

Compute, at collection time, the facts a person works out by hand when
triaging: whose move a PR is, why, since when and on whom; whether its CI
failures are its own or fail everywhere in the repository; how big and how
old it is; and where Jira and the code disagree. Each fact carries its
evidence. There is deliberately **no composite score** ([gh-96](gh-96.md)
principle 3).

## Requirements

### Where facts live

1. Pure functions in `internal/dash/facts.go` take the assembled snapshot,
   the people list, thresholds and `now` (the snapshot's `generated_at`), and
   return facts. They do no I/O, are deterministic, and run at the end of
   `assemble` (`internal/dash/assemble.go:77`).
2. PR facts go in an optional `facts` object on `PRInfo`; ticket facts in an
   optional `facts` object on `TicketInfo`; per-repository check facts in an
   optional snapshot-level `check_stats`.
3. Every fact that cannot be decided because an input is unknown is
   `unknown`, with the missing input named in `uncertain` — never false or
   zero.

### PR: whose move

4. `facts.move` is one of `author`, `reviewer`, `nobody`, `none`, `unknown`.
   `facts.reasons` lists **every** rule below that holds, in order; `move`
   comes from the first that holds.

   | # | Holds when | move | reason code |
   |---|---|---|---|
   | 1 | state is merged or closed | `none` | `closed` |
   | 2 | draft | `author` | `draft` |
   | 3 | some reviewer's latest review is `CHANGES_REQUESTED` and that reviewer has not been re-requested since | `author` | `changes_requested` |
   | 4 | `mergeable` is `conflicting` | `author` | `conflicts` |
   | 5 | a check fails that is not systemic (below) | `author` | `ci_failing` |
   | 6 | review decision is `APPROVED` | `author` | `approved_unmerged` |
   | 7 | at least one outstanding review request | `reviewer` | `awaiting_review`, plus `team_only` when every outstanding request is a team |
   | 8 | no outstanding requests and no approval | `nobody` | `no_reviewer` |

   Informational reasons that never decide `move`: `ci_systemic_only` (every
   failing check is systemic), `ci_pending`, `no_ticket` (no `ticket_keys`),
   `stale`.
5. `mergeable: unknown` does not stop evaluation; it is recorded in
   `uncertain`. Unknown requested reviewers (`reviewers_known: false`) make
   rules 7 and 8 undecidable, so `move` is `unknown` if no earlier rule held.
6. `facts.move_people` lists who holds the move: the author's login for
   `author`; the outstanding reviewers (`login` or `team:<slug>`) for
   `reviewer`, plus each configured person's login whose current
   `review_requested` involvement (gh-97) identifies a team request; empty
   otherwise. Deduplicate the list. The evidence distinguishes a direct
   request from a team request. The query `move_people:@me` (gh-100) is "my
   move", covering both my PRs and reviews requested from me through a team.

### PR: waiting

7. `facts.waiting_since`: for `reviewer`, the earliest active wait among
   outstanding requests, each starting at the later of `ready_at` and that
   reviewer's `requested_at`; for `nobody`, `ready_at`; for `author` by rule
   3, the submitting time of the blocking review; otherwise omitted. A
   request with no `requested_at` leaves its start unknown and is named in
   `uncertain`; use the earliest known active start as an approximation,
   label its resulting waiting duration a lower bound, and omit
   `waiting_since` if none is known.
   A newer request must not reset an older known wait. gh-104 replaces this
   approximation with timeline events when they are cached.
8. `facts.waiting_on`: outstanding reviewers for `reviewer`; omitted
   otherwise.
9. Durations (days waiting, age from `created_at`, days since update) are not
   stored; gh-100's field registry derives them from timestamps and
   `generated_at`.

### PR: size and staleness

10. `facts.size` = additions + deletions; `facts.size_bucket` is `xs` (< 10),
    `s` (< 100), `m` (< 500), `l` (< 2,000) or `xl`.
11. `facts.stale` is true when the PR is open and not updated for
    `[dash.facts] stale_days` days (default 30).

### CI: failing everywhere

12. For each repository, over open PRs in the snapshot that report a given
    check name: if failures ÷ runs ≥ `systemic_ratio` (default 0.6) and runs ≥
    `systemic_min_prs` (default 3), that check is **systemic** in that
    repository. `check_stats[repo]` lists every check name with `runs`,
    `failures` and `systemic`.
13. The evidence states the population honestly: "fails on 5 of 6 open PRs by
    the configured people in acme/api" — the snapshot sees only those PRs.
14. `facts.ci` is one of `green` (no failures or pending), `failing` (at least
    one non-systemic failure), `systemic_only`, `pending`, `none` (no checks)
    or `unknown`.

### Tickets: Jira vs code (needs gh-98)

15. `TicketInfo.facts.mismatches` lists every code that holds:

    | Code | Holds when |
    |---|---|
    | `code_merged_ticket_open` | at least one linked PR, all linked PRs merged or closed, at least one merged, and `status_category` is not `done` |
    | `ticket_done_code_open` | `status_category` is `done` and a linked PR is open |
    | `in_progress_no_code` | `status_category` is `in_progress`, in an active sprint, and no linked PR or workspace |
    | `in_progress_idle` | `status_category` is `in_progress` and no linked PR or workspace activity for `stale_days` |
    | `unassigned_in_sprint` | in an active sprint with no assignee |

    Without gh-98's `status_category` or sprints, the affected codes are
    unknown and listed in `uncertain`.
16. `TicketInfo.facts.linked_prs` lists the PRs linked to the ticket (by
    `pr → ticket` edges) as `[{id, ref, state}]`, where `state` is `draft`,
    `open`, `approved`, `merged` or `closed`. The ticket table (gh-101) and the
    sprint view (gh-105) show it.

### Evidence

17. Each reason and mismatch code has a one-line evidence string built from
    the inputs ("ready since Oct 8; review requested from team:web only";
    "PR acme/api#41 merged Oct 29; ticket In Progress"). The detail panel and
    tooltips show it (details on demand).

### Thresholds

18. `[dash.facts]`: `stale_days`, `systemic_ratio`, `systemic_min_prs`, with
    validation and errors that name the key and range.

## Out of scope

- Any composite score, weighting or ranking.
- Facts from timeline events (gh-104 refines `waiting_since` and rule 3).
- Writing anything back to GitHub or Jira.

## Acceptance criteria

- [ ] A table-driven test covers each `move` rule, each informational reason,
      rule precedence, and the multi-reason case (a draft with conflicts and a
      failing check lists all three).
- [ ] A team-only review request found in `@me`'s inventory sets
      `move_people` to include `@me`; adding a second reviewer later does not
      reset the older reviewer's `waiting_since`.
- [ ] Unknown inputs yield `unknown` and name the input in `uncertain`; no
      fact is false or zero because data was missing.
- [ ] On the fixture, a check failing on 5 of 6 PRs in one repository is
      systemic there and not in another repository where it fails once; a PR
      whose only failure is that check has `ci: systemic_only` and its move
      is not decided by CI.
- [ ] Each mismatch code has a passing and a non-passing fixture case.
- [ ] Evidence strings are present for every reason and mismatch.
- [ ] Facts are identical across two runs on the same input (determinism).
- [ ] `go test ./...` and `go vet ./...` pass.
