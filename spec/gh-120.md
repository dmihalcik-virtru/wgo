# gh-120 — Sprint planning view

**Issue:** https://github.com/dmihalcik-virtru/wgo/issues/120
**Epic:** [gh-96](gh-96.md) · Follow-up, not part of gh-96's acceptance criteria
**Sibling follow-ups:** [gh-121](gh-121.md) (retrospective), [gh-122](gh-122.md) (standup)

**Question it answers:** "What is scheduled in the upcoming sprints, what is
still unscheduled, and how do points and assignees compare across them before
a sprint starts?"

## Summary

A board-wide planning view. It shows each future sprint as a column with its
goal verbatim, dates, ticket count and points by status category, and beside
them the unscheduled candidates. Nothing here forecasts capacity: points and
assignee distribution are shown as fetched, and the view says so.

This is the one dash view whose population is **not** the configured people.
Planning needs the whole board's backlog, so the view labels its scope as
board-wide and states its coverage (returned count, truncation, search time).

## Before this change

- gh-98 reads future sprints' metadata only (`jira.ListSprints`) and does not
  search their tickets. It searches active sprints for configured people and
  unassigned tickets only.
- No dash code reads the board backlog. `[jira] board` names the board
  (`internal/config/config.go`).
- Team-wide ticket reads go through `jira.SearchIssues`, which already backs
  `wgo standup`.

## Requirements

1. An addon view `web/live-planning.js`, registered as `planning`.
2. **Population and coverage.** One board-wide search per refresh, through a
   new `dash.JobKind` `planning` on the existing `Refresher`, covering:
   - tickets in each future sprint of `[jira] board`;
   - backlog tickets not done and in no active or future sprint.

   The search is capped at 500 tickets per board (`[jira] planning_limit`).
   Truncation is recorded, and the view and extract show it beside the count.
   Its source is `jira_planning`, with freshness and reasons as gh-98 defines
   for `jira_sprints`. A partial result is never presented as the whole backlog.
3. **Sprint columns.** One column per future sprint, ordered by start date.
   Each shows:
   - name, start and end dates, and the goal verbatim (or "no sprint goal");
   - ticket count;
   - points by status category as one bar per column, each part labelled with
     points and count. Unestimated tickets are counted as "n unestimated", not
     as zero points. Tickets with unknown status category are counted as
     "n unknown status". The bar's denominator is points on tickets with a known
     status category.
   - assignee distribution: count and points per assignee, with unassigned
     shown as "unassigned". Assignees are labelled by display name; no bars
     are compared against any capacity figure.
4. **Candidates.** The backlog list, unscheduled tickets only, with the same
   row fields as gh-105 (key, summary, type, points, assignee, parent). Rows
   can be selected; the selection is shared with every view.
5. **Query.** gh-100 gains fields `sprint_state` (`active`, `future`, `none`)
   and `board_scope` (`configured_people_and_unassigned` for gh-98 tickets,
   `board` for planning tickets) so the query can separate them. Nonmatching
   rows are dimmed, not hidden, unless the toggle hides them. Column totals
   always cover every fetched ticket in that sprint.
6. **No writes.** Moving a candidate into a sprint is not offered. The view
   may show the `wgo` command or Jira link for the operator to act on
   elsewhere.
7. **Extract.** "Copy as Markdown" requests
   `/api/extract?view=planning&board=<id>&q=<query>`. `wgo dash --md --view
   planning --query EXPR` calls the same renderer. The provenance footer names
   the board-wide scope, each sprint's returned count and truncation, the
   active query, and source freshness.
8. **Explanations.** With no `[jira] board`, no future sprints, or an
   unknown or errored planning search, the view names the missing piece and
   its remedy (for example `[jira] board = <id>` or `acli jira auth login`)
   instead of an empty board.

## Open questions

- Whether `acli jira workitem search` can express "board backlog" directly or
  needs a JQL form. The implementer records the answer in the delivery notes
  and follows gh-98 requirement 4 for any field that cannot be fetched.
- Whether 500 tickets is the right default cap. It is configurable; the spec
  picks it so one search stays under the gh-98 sprint bound.

## Out of scope

- Writing sprint membership, ranking, or drag-and-drop planning.
- Capacity, velocity, burndown, or any forecast of what fits in a sprint.
- Boards other than `[jira] board`.
- Sprint retrospectives and closed sprints (gh-121).

## Acceptance criteria

- [ ] The fixture board shows two future sprints and a backlog with
      unscheduled, unestimated and unknown-status tickets, each counted and
      labelled separately.
- [ ] Each column names the board-wide scope and its coverage; a truncated
      search is labelled in the view and the extract.
- [ ] Assignee distribution shows unassigned tickets and has no capacity
      figure anywhere in the view or extract.
- [ ] A query changes the match count and dims rows; column totals stay for
      all fetched tickets.
- [ ] The Markdown planning summary matches a golden file and is
      byte-for-byte identical from the CLI and `/api/extract` for the same
      snapshot and query.
- [ ] Missing board, missing sprints and failed searches produce the
      explanatory state, not zero counts.
- [ ] Keyboard-only use and a colour-vision-deficiency simulation pass
      (screenshots in the PR, light and dark).
- [ ] `go test ./...` passes.
