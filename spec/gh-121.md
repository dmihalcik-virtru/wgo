# gh-121 — Sprint retrospective

**Issue:** https://github.com/dmihalcik-virtru/wgo/issues/121
**Epic:** [gh-96](gh-96.md) · Follow-up, not part of gh-96's acceptance criteria
**Sibling follow-ups:** [gh-120](gh-120.md) (planning), [gh-122](gh-122.md) (standup)

**Question it answers:** "For a closed sprint, what was in it when it closed,
what was done, and what carried over?"

## Summary

Jira's live ticket state changes after a sprint closes: tickets are moved,
re-estimated, re-sprinted. So a retrospective built from current state is
wrong by the time anyone reads it. This spec captures a **close record** for
each sprint at the moment wgo first observes it closing, and the retrospective
reads only those records.

A sprint with no close record is shown as unknown. It is never reconstructed
from current ticket state.

## Before this change

- gh-98 reads active sprints' tickets and the state of each board sprint
  (`jira.ListSprints`). It does not store history.
- `jiracache` holds the latest ticket info only.
- The `Refresher` (`internal/dash/remote.go`) runs `sprints` jobs on a 15-minute
  TTL (gh-98), so a sprint closing is observed on the next refresh after it
  happens, not at the instant it closes.

## Requirements

1. **Detecting close.** Each `sprints` refresh compares every board sprint's
   state with the last state stored for it. On a transition from `active` to
   `closed`, the refresher captures a close record for that sprint, once.
   Capture is idempotent: a record that exists is not overwritten.
2. **Close record contents**, stored as JSON under
   `~/.wgo/state/sprint-close/<board>/<sprint-id>.json`:
   - sprint id, name, start, end, and the goal verbatim;
   - `closed_observed_at`: when wgo saw the close, which may be later than the
     real close;
   - `captured_at`;
   - for each ticket in the sprint at close: key, summary, status category and
     status name, points (or unknown), assignee account ID and display name,
     type, resolution, `resolved_at`, and the other sprints it belongs to;
   - coverage: scope, returned count, `truncated`, and the search source's
     freshness.
3. **Search scope for close.** Capture uses a sprint-membership search for all
   assignees, not gh-98's configured-people search. A retrospective of part of
   a sprint would show carryover and completion wrongly. The search is capped
   at 500 tickets (`[jira] retro_limit`). A truncated record is kept but marked
   incomplete in the view and extract; it is not a complete retrospective.
4. **Definitions.** Written into the record and repeated in every output:
   - *Done*: status category `done` at close.
   - *Carried over*: in the sprint at close and not done at close.
   - *Points* are the points fetched at close. Unestimated tickets are counted
     separately and never as zero.
   Whether a carried-over ticket was re-added to the next sprint is read from
   the next sprint's record, when that record exists. Until then it shows as
   "next sprint not captured".
5. **No backfill.** Sprints that closed before this feature shipped, or while
   wgo was not running, have no record. This spec does not rebuild them from
   Jira changelogs. Changelog backfill is a follow-up, to be taken only if
   `acli` can return sprint change history, which the implementer records in
   the delivery notes.
6. **Retention.** Keep the most recent 12 close records per board and prune
   older ones at capture. At a four-week cadence that is about one year.
7. **View.** An addon `web/live-retro.js`, registered as `retro`. A selector
   picks a closed sprint from its records (`sprint=` in the URL). The header
   shows the goal verbatim, dates, `closed_observed_at` and `captured_at`. The
   body shows:
   - points and ticket counts by status at close, each part labelled;
   - the done list and the carried-over list, each with keys, summary and
     points.

   Retrospective numbers come only from the record. The view does not
   overwrite them with current Jira state. A ticket's current status may be
   shown in a separate, labelled column "now", so a later edit is visible
   without changing the record.
8. **Sprints without a record** show "no close record: closed before capture or
   while wgo was not running", never zero tickets.
9. **Query.** gh-100's query applies to the list of tickets in the record
   (for example `status_category:done`, `carried_over:true`). Totals always
   cover every ticket in the record.
10. **Extract.** `/api/extract?view=retro&sprint=<id>&q=<query>`, and
    `wgo dash --md --view retro --sprint ID`, with the same renderer. The
    footer names the record's `closed_observed_at`, `captured_at`, coverage and
    truncation.

## Open questions

- Whether `acli jira workitem search` can return sprint membership for all
  assignees at the needed size. The implementer records this in the delivery
  notes. If it cannot, the feature is blocked, not degraded to the
  configured-people search.
- Whether 12 records is the right retention. The number is configurable.

## Out of scope

- Burndown charts, velocity, team capacity, or a forecast.
- Changelog backfill of past sprints (see requirement 5).
- Planning and standup views (gh-120, gh-122).
- Writing to Jira.

## Acceptance criteria

- [ ] A fixture sprint moving from `active` to `closed` writes exactly one
      record; a second refresh does not change it.
- [ ] Editing a ticket in the fixture after close (status, points, sprint)
      does not change the record or the retrospective totals; the "now" column
      shows the change.
- [ ] A sprint with no record shows the explanatory state, not zero.
- [ ] A truncated capture is labelled incomplete in the view and the extract.
- [ ] Records beyond the retention limit are pruned at capture.
- [ ] The Markdown retrospective matches a golden file and is byte-for-byte
      identical from the CLI and `/api/extract` for the same record and query.
- [ ] Keyboard-only use and a colour-vision-deficiency simulation pass
      (screenshots in the PR, light and dark).
- [ ] `go test ./...` passes.
