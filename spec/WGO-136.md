# WGO-136 — `wgo rig`: pinned multi-checkout Go workspaces

## Summary

Add `wgo rig`, a command that materialises one editable, tag-pinned, sparse checkout
per Go module a downstream artifact depends on — several per repo where needed — and
generates a `go.work` tying them together. The result is a source tree that mirrors a
shipped binary closely enough to attach a debugger and reproduce client issues.

A rig is a third on-disk layout alongside `mains_dir` and `worktrees_dir`: pinned rather
than branch-tracking, disposable, and intentionally multi-per-repo.

## Problem / Motivation

Our Go monorepos carry many `go.mod` files. Go's module tagging convention for a module
in a subdirectory is `<subdir>/<version>`, so each module in a monorepo is released
independently, and a downstream artifact pins **several different commits of the same
repo simultaneously**.

`virtru-corp/data-security-platform@v2.7.1` requires 7 `opentdf` modules plus 1
indirect. Those pins span **7 distinct commits** of `opentdf/platform`, plus a second
repo entirely:

| module | version | tag | commit |
|---|---|---|---|
| `platform/service` | v0.11.6 | `service/v0.11.6` | `6a5827d7` |
| `platform/sdk` | v0.10.1 | `sdk/v0.10.1` | `a9262237` |
| `platform/protocol/go` | v0.13.0 | `protocol/go/v0.13.0` | `22faa49a` |
| `platform/lib/ocrypto` | v0.7.0 | `lib/ocrypto/v0.7.0` | `a2fa7a98` |
| `platform/lib/identifier` | v0.2.0 | `lib/identifier/v0.2.0` | `7fab0940` |
| `platform/lib/fixtures` | v0.3.0 | `lib/fixtures/v0.3.0` | `237edab0` |
| `platform/lib/flattening` (indirect) | v0.1.3 | `lib/flattening/v0.1.3` | `a2323482` |
| `opentdf/otdfctl` (separate repo) | v0.26.2 | `v0.26.2` | — |

To reproduce a customer issue against a released build today you either read
non-editable source out of `$GOMODCACHE`, or hand-assemble a pile of checkouts and a
`go.work` by hand. Neither gives you a tree you can set breakpoints in, patch, and
rebuild while being confident it matches what shipped.

Existing `wgo` commands cannot express this. `wgo to` and `wgo add` create one workspace
per *bookmark*, keyed on branch names, tracking a moving tip. A rig needs N workspaces
of one repo at N *tags*, with no bookmarks at all.

## Proposed Solution

### 1. jj workspaces provide the mechanism

`jj workspace add` already gives N working copies over one repo store, and secondary
workspaces share the mains clone's `.jj/repo`, so only materialised files cost disk.
Verified on jj 0.44:

- git tags resolve as revset symbols; `present(tags(exact:"service/v0.11.6"))` is
  unambiguous against same-named bookmarks and returns empty rather than erroring on a
  miss.
- pseudo-version commit hashes resolve directly (`87305bdcc192`).
- `jj workspace add --sparse-patterns=empty -r <tag>` followed by
  `jj sparse set --clear --add <subdir>` yields a *partial* checkout of just the module.
- `-r` sets the working-copy commit's **parent**, so content equals the tag and edits
  land in a child change — editable without disturbing the pin.

Sparse matters: `opentdf/platform` is 261M but `service/` is 7.2M. Seven sparse
checkouts cost tens of MB rather than ~1.8G, and the editor indexes seven small trees.

### 2. Module path → repository mapping must be structural

`github.com/opentdf/otdfctl` is a separate repository, while `opentdf/platform` *also*
contains a module named `github.com/opentdf/platform/otdfctl`. Prefix matching gets this
wrong. The rule is: strip any trailing major-version element, then the first two path
elements after a recognised code host are the repository; everything after is the
subdirectory.

### 3. Layout

```
<rig.dir>/dsp-2.7.1/
  rig.toml            # manifest — the only persistent state
  go.work  go.work.sum
  env.sh  .envrc      # exports an absolute GOWORK
  CLAUDE.md  README.md  .gitignore
  src/
    data-security-platform-v2.7.1/    # FULL (root module + ./sdk replace target)
    platform-service-v0.11.6/         # sparse: service
    platform-sdk-v0.10.1/             # sparse: sdk
    platform-protocol-go-v0.13.0/     # sparse: protocol/go
    platform-lib-ocrypto-v0.7.0/      # sparse: lib/ocrypto
    platform-lib-identifier-v0.2.0/   # sparse: lib/identifier
    platform-lib-fixtures-v0.3.0/     # sparse: lib/fixtures
    platform-lib-flattening-v0.1.3/   # sparse: lib/flattening
    otdfctl-v0.26.2/                  # FULL (root module)
```

Checkouts are keyed by **(repo, commit)**: two modules resolving to one commit share a
workspace with a unioned sparse set. There are no symlinks anywhere in a rig, because
`go work use` does not resolve them.

### 4. MVS drift is a first-class concern

Every `use` directive promotes a module to a main module, making its full requirement
graph an MVS root. Third-party versions can therefore only move **up** relative to what
the artifact shipped. A rig that silently builds against a different gRPC than
production is worse than no rig at all, so `wgo rig verify` is part of the feature
rather than later polish.

## Inputs / Outputs / Contracts

### `wgo rig new <name>`

```
wgo rig new dsp-2.7.1 --from virtru-corp/data-security-platform@v2.7.1
cd $(wgo rig new dsp-2.7.1 --from ...)     # stdout is the rig path
```

**Flags:**
- `--from <owner/repo>@<ref>` — resolve pins from a tagged downstream repo
- `--from-binary <path>` — resolve pins from a built artifact's embedded build info
- `-m, --module <path>@<version>` — add a module explicitly (repeatable)
- `--org <module-path-prefix>` — treat this prefix as in-org (repeatable, overrides config)
- `--full` — full checkouts instead of sparse
- `--no-verify` — skip the post-create drift check
- `--dry-run` — print the plan (checkouts, sparse sets, `go.work`) and exit

**Algorithm:**
1. `resolveCwd()` → `config.Init()`/`Get()` → `jj.NewCLI()`; require `gotool.Available()`
2. Validate `cfg.Rig.Dir`; error if `<rig.dir>/<name>` exists and holds no matching `rig.toml`
3. Resolve the primary pin, materialise its checkout
4. Compute the build list — for `--from`, `go list -deps` in the primary checkout **with
   that repo's own `go.work`**; for `--from-binary`, the `dep` lines of `go version -m`
5. Filter to in-org modules, map each to `(repo, subdir, tag)`, resolve each tag to a
   commit, group by `(repo, commit)`
6. Widen each sparse set to cover relative `replace` targets; suppress modules already
   served by a local replace inside another checkout
7. `WorkspaceAdd` each checkout with `Sparse: empty` and a descriptive `-m`, then
   `SparseSet`
8. Render `go.work`, validate with `go work edit -fmt`, write `rig.toml` and the
   generated helper files
9. Unless `--no-verify`, run the drift check and report
10. `fmt.Println(rigRoot)` — stdout only; all logging to stderr

### `wgo rig ls | show [name] | rm <name> | sync [name] | add <name> -m mod@ver`

- `ls` — table on TTY, one path per line when piped, `--format=json`
- `show` — module→checkout→commit table, sparse sets, skips, freeze state;
  `--env` prints shell exports for `eval "$(...)"`
- `rm` — `jj workspace forget` each recorded workspace then remove the tree; refuses on a
  dirty checkout without `--force`
- `sync` — re-resolve the source, add/remove/rewiden checkouts, rewrite `go.work`
- `add` — add one module by hand

### `wgo rig verify [name]`

**Flags:** `--all` (compare the full build list, not just package-contributing modules),
`--freeze`, `--unfreeze <module>`, `--format=json`, `--write-back`

Compares the manifest baseline against `go list` run with `GOWORK=<rig>/go.work`,
excluding modules the rig replaces. Classifies each difference as Upgraded, Downgraded,
Added or Missing. Exit 1 on any up/downgrade.

`--freeze` writes `replace <mod> => <mod> <baseline-version>` into `go.work` via
`go work edit -replace`, then re-runs `go build ./...` and reports, because forcing a
version down can break a member module.

### New packages

- `internal/gomod` — pure module identity: `Origin{Host,Owner,Repo,Subdir,Major}`,
  `ParseOrigin`, `TagFor`, `Revset`, `InOrg`, `LocalReplaceTargets`, `ParseBuildInfo`,
  `ParseModuleList`, `MaxGoVersion`. Thin wrapper over `golang.org/x/mod`.
- `internal/gotool` — `go` toolchain shell-out, modelled on `internal/lfs`.
- `internal/rig` — `Manifest`, `Planner`, `RenderGoWork`, `Materializer`, `Verify`.

### Changes to existing packages

- `internal/jj` — add `SparseSet`, `SparseList`, `GitFetchTags`; change `WorkspaceAdd`
  to take a `WorkspaceAddOpts` (adds `Message` and `Sparse`).
- `internal/config` — `RigConfig{Dir, OrgPrefixes, Sparse, VerifyOnNew, Freeze}`.
- `internal/discovery` — `ExcludeRoots`.
- `internal/cleanup` — skip rig workspaces.
- `internal/cmd` — new `rig.go`; `newDiscovery(cfg)` helper replacing 11 duplicated
  `discovery.New(...)` call sites; a guard in `join`.

## Edge Cases & Constraints

- **The primary repo may have its own committed `go.work`.**
  `data-security-platform` does (`use (. ./sdk)` at v2.7.1). Three consequences: the
  rig's `go.work` cannot live at the primary checkout root; the baseline build list must
  be computed *with* that `go.work` (its `sdk` submodule pins `platform/service v0.7.2`
  against root's `v0.11.6`, so a single-module baseline is simply wrong); and the rig
  must mirror the repo's own `use` list. Because Go walks ancestors to find a `go.work`,
  every `go` invocation must set `GOWORK` explicitly to an absolute path. This is the
  single most important runtime detail of the feature.
- **Relative replaces can point upward.** `platform/test/integration/go.mod` uses
  `=> ../../lib/fixtures`. Sparse widening runs unconditionally; `../` targets stay
  inside the repo so widening handles them. A target escaping the repo root cannot be
  satisfied — warn and record it as skipped.
- **Locally replaced modules get no checkout of their own.**
  `…/data-security-platform/sdk/v2` is pinned at a pseudo-version but replaced with
  `./sdk`, so it is served from the primary checkout.
- **Major-version suffixes.** `…/data-security-platform/sdk/v2 v2.7.1` maps to tag
  `sdk/v2.7.1`, not `sdk/v2/v2.7.1`.
- **Pseudo-versions** resolve to their embedded 12-hex commit, not a tag.
- **Tag missing locally**: fetch tags then retry; on continued failure, error naming the
  exact `jj git fetch` to run by hand. The hint is version-dependent: a pseudo-version
  names a commit directly, so a missing one is not a missing tag and suggesting `-t`
  would send the user down the wrong path.
- **In-org module in an unreachable repo** (private, deleted, vanity import): warn,
  record in `manifest.Skipped`, and continue. Aborting a nine-checkout rig over one
  unreachable module is hostile. **Exception: the primary.** A rig exists to put the
  artifact's own source under a debugger, so a primary that got no checkout is a hard
  error — otherwise the rig builds, validates and reports success with the one module
  that mattered quietly absent.
- **No org prefixes is a hard error.** An empty filter admits nothing, so every
  dependency is skipped and the rig is the primary alone — a legal manifest, a useless
  rig, and it looks like success.
- **Module subdir absent at the resolved commit**: hard error. This means the
  module→repo mapping is wrong, and continuing would produce a silently wrong build.
- **`jj sparse set` must run with cwd set to the target workspace.** Using `runR`
  (`-R <mainClone>`) would rewrite the **main clone's** sparse patterns — a
  repo-damaging footgun that must be doc-commented at the call site.
- **Rig workspaces carry no bookmark.** They must therefore be excluded from
  `internal/cleanup`, which reaches them via `ListWorkspaces(mainClone)` rather than
  through `rig.dir`, so a discovery-level exclusion does not cover it. This is latent
  today (`workspaceBookmark` reads bookmarks on `@` only, and a rig `@` has none) but
  becomes live the moment a local bookmark sits on a pinned tag commit. Each workspace
  is given a descriptive `-m` so `jj log`/`jj workspace list` remain readable without a
  bookmark.
- **`wgo join` infers `sharedRoot = filepath.Dir(cwd)`** and would create sibling
  workspaces inside `<rig>/src`, so it needs an early guard. **`wgo add` does not:**
  it always builds its shared root under `worktrees_dir`, so it cannot scribble
  inside a rig and is deliberately left unguarded. It does still infer `ownerRepo`
  from cwd, so running it inside a rig checkout creates ordinary branch work
  against that pinned repo — surprising, but landing in the normal worktree tree
  rather than in the rig. Accepted rather than guarded, to keep one code path.
- **`go work sync` is destructive** — it writes the workspace build list back into every
  member's `go.mod`, dirtying every checkout. Never called implicitly; reachable only
  behind an explicit `--write-back`.
- **Idempotency and rollback.** Re-running `rig new` over a matching `rig.toml` is
  treated as `sync`. On failure, roll back in reverse order, forgetting and removing
  only what *this run* created, and never touching a workspace that is neither recorded
  in our manifest nor carrying our `rig-<name>-` prefix.
- **Workspace name collisions.** Names are `rig-<rig>-<short8>`, where `short8` is the
  first 8 characters of the checkout's commit. The commit — not the checkout dir — is
  the discriminator, and it is appended *after* `gh.SanitizeBranch` (60-char cap) so
  truncation cannot eat the part that makes the name unique. Rig names are therefore
  capped at `MaxNameLen` (= 60 − len("rig-") − 1 − 8) rather than truncated. The final
  name is persisted and never recomputed.
- **`go` not on PATH**: fail before touching disk, since the build list determines which
  checkouts exist.
- **Repo-root modules gain nothing from sparse**: fall back to full and note it.

## Out of Scope

- Non-Go ecosystems (npm, Cargo, Maven). The `rig` concept generalises, but this work
  implements Go only.
- Non-GitHub code hosts and vanity import paths. `ParseOrigin` returns
  `ErrUnsupportedHost` for these and the module is skipped rather than guessed at.
- Building, running or shipping the artifact. A rig produces a source tree and a
  `go.work`; `go build` and `dlv` are the user's to invoke.
- Automatic rebasing or updating of pins to newer tags. A rig is deliberately frozen;
  `wgo rig sync` re-resolves the *same* source, it does not bump versions.
- Publishing changes made inside a rig. Rig checkouts have no bookmark and no PR
  workflow; to turn a fix into a PR, use `wgo to`/`wgo add` in the normal worktree tree.
- Cross-rig sharing or deduplication of checkouts between two rigs.
- `wgo status` integration beyond a summary section, and any watch-mode support.
- Vendoring, or any attempt to make the rig hermetic against `$GOMODCACHE` for
  out-of-org dependencies.

- [ ] Each platform checkout contains only its module's subdirectory; `du -sh` on each is single-digit MB

- [ ] `GOWORK=<rig>/go.work go build ./...` succeeds
- [ ] `jj -R <platform clone> workspace list` shows 7 `rig-`prefixed workspaces, each with a descriptive message
- [ ] `wgo rig verify` on a `--from-binary` rig reports zero drift
- [ ] `wgo rig verify` detects an injected third-party upgrade, exits 1, and `--freeze` restores a passing `go build`
- [ ] `wgo clean` proposes no candidates for rig workspaces, including when a bookmark sits on a pinned commit
- [ ] `wgo to`, `wgo ls`, `wgo status` never list rig checkouts
- [ ] `wgo join` refuses to run inside a rig with an error pointing at `wgo rig add`
- [ ] A failure partway through `rig new` leaves no workspaces and no rig directory behind
- [ ] `wgo rig rm dsp-2.7.1` forgets every workspace and removes the tree; refuses on a dirty checkout without `--force`
- [ ] An unreachable in-org module is skipped with a warning and recorded in `rig.toml`, rather than aborting the rig
- [ ] `wgo doctor` reports a checkout that has been moved off its pinned commit
