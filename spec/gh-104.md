# gh-104 — PR timelines

**Issue:** https://github.com/dmihalcik-virtru/wgo/issues/104
**Epic:** [gh-96](gh-96.md) · **Wave 4** · Needs gh-97 and gh-100; refines gh-99

**Question it answers:** "Where has each PR's time gone — in draft, waiting on
whom, or with changes requested?"

## Summary

Fetch each PR's review history and draw one line per PR on a shared time
axis, segmented by state, after Plaisant & Shneiderman's LifeLines (CHI '96).
A PR that has sat with one reviewer for six weeks stands out at once. The same
events make gh-99's "waiting since" exact.

## Requirements

### Data

1. Per PR, cache timeline events from the GraphQL `timelineItems`
   connection: `ReadyForReviewEvent`, `ConvertToDraftEvent`,
   `ReviewRequestedEvent` (reviewer), `ReviewRequestRemovedEvent`,
   `PullRequestReview` (author, state), `MergedEvent`, `ClosedEvent`,
   `ReopenedEvent`. Paginate 100 at a time.
2. Cache in `internal/inventory` (gh-97), keyed by repository and number, with
   the PR's `updated_at`. Refetch only when `updated_at` changes. Refresh in
   the background `Refresher` only, at most 50 PRs per cycle, open PRs first,
   then closed-recent. A source `github_timelines` reports coverage ("120 of
   195 PRs") and freshness.
3. GET routes stay network-free; the page never triggers a fetch.

### Segments

4. A pure function in `internal/dash` turns events into segments:
   - `draft`
   - `waiting` (with the outstanding reviewers): from a request to that
     reviewer's review or the request's removal
   - `changes_requested`: from a `CHANGES_REQUESTED` review to the next
     request or ready event
   - `approved`: approved and not merged
   - `unattended`: ready, nobody requested, no approval
   - `merged` / `closed`

   Overlapping waits on several reviewers form one segment listing all of
   them; an expanded row shows one lane per reviewer.
5. When a PR's timeline is cached, gh-99 uses it:
   - `waiting_since` becomes the start of the current `waiting` or
     `unattended` segment;
   - rule 3 ("changes requested and not re-requested") is decided from
     events.

   Otherwise gh-99's approximation stands, and the evidence says which
   applies.

### View

6. An addon view `web/live-timeline.js`, registered as `timeline`:
   - one row per PR row of the query, ordered by the table's sort;
   - a linear time axis shared by all rows, with a "now" line;
   - the PR ref as a direct label on the left and its current state on the
     right.
7. Segment encoding uses neutral fills distinguished by pattern and a text
   label when the segment is wide enough: draft hatched, waiting solid grey,
   changes requested outlined, approved light. The accent colour marks only
   time waiting on the operator (`@me` or their teams). Review events are
   ticks with `✓` or `✕`.
8. Brushing the axis zooms the view (view state `t=a..b` in the URL); it does
   not filter. A control applies the brushed range as `when:a..b` if the
   operator wants a filter.
9. Hover or focus shows the segment's reviewers, start, end and duration;
   each row has a text summary for screen readers ("draft 12d, waiting on bob
   30d, approved 2d").
10. PRs without a cached timeline show a single bar from `created_at` to now,
    labelled "history not fetched yet".

## Out of scope

- Commit or push events, CI re-runs and comments.
- Organisation-wide review-latency statistics.

## Acceptance criteria

- [ ] The segment function is covered by table-driven tests: re-requests,
      removed requests, several reviewers, draft round-trips, reopen, and team
      requests.
- [ ] Timelines refresh only for PRs whose `updated_at` changed, and at most
      50 per cycle (test with a fake server and call counts).
- [ ] `github_timelines` reports coverage; GET purity tests pass.
- [ ] gh-99 `waiting_since` uses timeline data when present; its evidence says
      which source applied.
- [ ] The view renders the fixture with direct labels, the now line, the
      accent only on time waiting on the operator, and text summaries;
      screenshots in light and dark in the PR.
- [ ] `go test ./...` passes.
