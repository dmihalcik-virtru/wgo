# gh-122 — Today / standup view

**Issue:** https://github.com/dmihalcik-virtru/wgo/issues/122
**Epic:** [gh-96](gh-96.md) · Follow-up, not part of gh-96's acceptance criteria
**Sibling follow-ups:** [gh-120](gh-120.md) (planning), [gh-121](gh-121.md) (retrospective)

**Question it answers:** "What changed for me in this window, what is blocked
now, and what should I do next?"

## Summary

A standup view with three parts: what changed in an explicit calendar window,
what is blocked right now, and a next-action queue across PRs, Jira tickets
and plan items. Work that is in flight but not in any sprint stays visible,
as `wgo standup` shows it today.

Changes are derived from **timestamps the sources already record**, not from
diffs between snapshots. wgo does not record every change during a day, so
the view says what it can and cannot see.

## Before this change

- `wgo standup` (`internal/cmd/standup.go`) gathers in-flight work from jj,
  `.plan` files and Jira, and prints text. Its output is the baseline this
  spec must not change.
- gh-70's "since last look" marks new activity against a stored timestamp. It
  is not a calendar window and not a log of changes.
- gh-97 fetches PR facts; gh-98 fetches ticket facts including `updated_at`.

## Requirements

1. **Window.** An explicit window in local time:
   - CLI: `wgo dash --md --view standup --window yesterday`, or `today`, or
     `<date>..<date>`;
   - browser: a window control in the filter panel, default `today`.

   The window resolves to `[start, end)` in local time. The header shows the
   resolved range and the time zone, so a DST-shifted day is visible.
2. **Changes come from source timestamps.** Each change is an event with the
   source's own timestamp:
   - PRs authored by a configured person: created, merged or closed, a review
     submitted (`submittedAt`), a comment, and the latest commit date. gh-97
     fetches the timestamps this needs; where it does not, the event type is
     `unknown`, not absent.
   - Local work: change timestamps wgo already reads from the jj DAG (bookmark
     moves, new commits in the window).
   - Jira: tickets assigned to a configured person with `updated_at` in the
     window. Without changelog access (gh-98), the event reads "updated", not
     "moved to Done".
   - A footer line states the limit: intermediate states inside the window that
     were overwritten before any read are not shown.
3. **Blocked now.** Current facts only, not window-scoped, each with its
   evidence:
   - the operator's PRs with changes requested;
   - the operator's PRs with a failing required check (named, from gh-97);
   - PRs with a merge conflict (`mergeable` from gh-97);
   - review requests to the operator on PRs that have waited, shown with the
     request date;
   - in-progress tickets with no linked PR.

   Each item names its source and freshness. Unknown inputs show as unknown,
   never as "not blocked". The view does not assign a blocked verdict to an
   item beyond the fact listed.
4. **Next-action queue.** One list drawn from PRs, assigned tickets and plan
   items (from the existing `.plan` parsing). Each row is a fact with its
   source, age and link, for example "review requested from you, 3 days" or
   "plan item in progress, no PR". Default order is by source, then age; the
   order is shown and can be changed by sort keys. No composite priority.
5. **In flight outside sprints.** Work in flight with no sprint (the
   `wgo standup` case) appears in its own section, "in flight, not in a
   sprint", so a non-sprint project is not lost when sprint data exists.
6. **`wgo standup` is unchanged.** Its text output and flags do not change in
   this spec. The new view may reuse its data gathering. A golden-file test
   pins the current output on the fixture.
7. **View.** An addon `web/live-standup.js`, registered as `standup`, with four
   sections: Changed in window, Blocked now, Next actions, In flight outside
   sprints. Each section shows a count and the sources it covers.
8. **Query.** gh-100 applies to the rows of every section (for example
   `repo:acme/api`, `author:me`). Counts always name the query.
9. **Extract.** `/api/extract?view=standup&window=<w>&q=<query>`, and
   `wgo dash --md --view standup --window <w>`, with the same renderer. The
   footer names the window, time zone, each source's freshness, and the limit
   in requirement 2.

## Open questions

- Whether gh-97 should fetch review and comment timestamps for every
  configured person's PRs, or only for PRs already in the window. The default
  here is the former, which is what the window needs; the cost is recorded in
  gh-97's delivery notes.
- Whether plan items carry dates. Where they do not, they appear under "Next
  actions" with no age.

## Out of scope

- Writing to GitHub, Jira, or the plan file.
- Sending the standup anywhere (Slack, email) or scheduling it.
- Time tracking, durations per task, or a priority score.
- Changelog-based Jira status history (gh-98 decides whether it is possible).

## Acceptance criteria

- [ ] Window resolution has tests for `today`, `yesterday`, an explicit range,
      and a DST-changing day in a non-UTC zone.
- [ ] Each event type reads its source timestamp; an event whose timestamp is
      missing shows as unknown, not dropped.
- [ ] Blocked items on the fixture list their evidence and source; an unknown
      input is shown as unknown.
- [ ] `wgo standup` output on the fixture matches its golden file before and
      after this change.
- [ ] The standup section counts match between the browser, `/api/extract`
      and `wgo dash --md` for the same snapshot, window and query.
- [ ] The footer states the intermediate-state limit in every output.
- [ ] Keyboard-only use and a colour-vision-deficiency simulation pass
      (screenshots in the PR, light and dark).
- [ ] `go test ./...` passes.
