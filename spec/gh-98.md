# gh-98 — Jira ticket and sprint facts

**Issue:** https://github.com/dmihalcik-virtru/wgo/issues/98
**Epic:** [gh-96](gh-96.md) · **Wave 1** · Unblocks gh-99's ticket facts and gh-105

## Summary

Give ticket nodes the facts that sprint hygiene needs — status category,
type, sprint, story points, parent epic, team, resolution — and add the
active sprint itself: its goal and dates, and every ticket in it assigned to
the configured people or unassigned, including tickets with no PR or workspace.

## Before this change

- `jiracache.Info` (`internal/jiracache/jiracache.go:56`) holds status,
  assignee and site. It is fetched with `acli jira workitem view --fields
  summary,description,status,priority,assignee` (`internal/jira/client.go:173`)
  and read on the statusline hot path.
- Ticket nodes exist only for tickets parsed from bookmarks
  (`Collector.ticketNode`, `internal/dash/assemble.go`); gh-97 adds tickets
  parsed from PRs.
- `jira.ListSprints` (`internal/jira/client.go:101`) and `jira.SearchIssues`
  already back `wgo standup`, which requests only an "acli-allowed" field set
  (`internal/cmd/standup.go:56`). `[jira] board` names the default board.
- Story points, sprint and team are site-specific custom fields whose IDs
  differ per site (story points is `customfield_10016` on some sites and
  `customfield_10004` on others).
- In practice `acli` authentication expires; the dash must keep working
  without it.

## Requirements

### Ticket facts

1. Extend `jiracache.Info` and `dash.TicketInfo` (`internal/dash/model.go:228`)
   with optional fields:

   | Field | Meaning |
   |---|---|
   | `summary` | issue summary (fills `TicketInfo.Title`) |
   | `status_category` | `todo`, `in_progress` or `done` (Jira `statusCategory`) |
   | `type`, `priority` | names |
   | `sprints` | `[{id, name, state}]`, `state` one of `active`, `future`, `closed` |
   | `story_points` | number |
   | `parent` | `{key, summary, type}` (epic or parent issue) |
   | `team` | team field value, display name |
   | `components`, `labels` | lists of names |
   | `resolution`, `resolved_at`, `created_at`, `updated_at` | as Jira reports |
   | `assignee_id` | account ID, for matching people |

2. Old cache entries without these fields stay readable; their new fields are
   unknown until the next refresh. The statusline path stays a single cache
   read and gains no synchronous call.

### Site field mapping

3. `[jira.fields]` maps logical names to site field IDs: `story_points`,
   `sprint`, `team`, `epic_link` (legacy parent link). Any that are unset are
   discovered once by field name ("Story Points", "Sprint", "Team") and
   cached for 7 days under `~/.wgo/cache/jira/fields.json`.
4. Before relying on `acli`, the implementer verifies which of these fields
   `acli jira workitem view` and `acli jira workitem search --fields` can
   return, and records the result in this spec's Delivery notes. If a field
   cannot be fetched, it stays unknown and a diagnostic names the config key
   or limitation — never a silent blank.

### Sprint data

5. When `[jira] board` is set, read the board's active and future sprints
   (`jira.ListSprints`) into a new node kind `sprint` with `SprintInfo{id,
   name, state, start, end, goal, board}`. For active sprints, `SprintInfo`
   also records `ticket_scope: "configured_people_and_unassigned"`,
   `ticket_lookup` freshness, `ticket_fetched_at`, the number of tickets
   returned, and `truncated`. These describe ticket coverage
   independently of sprint metadata; the returned count is omitted when
   there is no cached ticket result. Cache per board with a 15-minute TTL;
   refresh through a new `dash.JobKind` `sprints` on the existing `Refresher`.
6. For each active sprint, search for its unassigned tickets and tickets
   assigned to any configured person with a Jira identity (gh-97's
   `[[dash.people]]`; default `currentUser()` and `[pair] teammate_jira`; if
   gh-97 has not landed, this spec adds `[[dash.people]]` as gh-97 specifies
   it). Deduplicate by ticket key. Add a ticket node for each, whether or not
   a PR or bookmark leads to it. Tickets assigned to other people are outside
   this search, so its counts are never labelled as board-wide sprint totals.
7. Edges: `ticket → sprint` (new kind `in_sprint`) for every ticket whose
   `sprints` includes a sprint node. A ticket that no PR, bookmark or effort
   leads to attaches to a group effort `sprint:<id>` (new group `sprint`,
   ordered after `repo` groups and before Ungrouped) through the `tracks`
   edge kind from gh-97. If gh-97 has not landed, this spec adds `tracks`.
8. Sources: `jira` keeps its meaning and covers the new fields; a new source
   `jira_sprints` reports sprint metadata and ticket-search freshness. A
   successful sprint list with a failed or unavailable ticket search retains
   the sprint metadata but sets that sprint's `ticket_lookup` to `stale`,
   `unknown` or `error` as appropriate; it never means zero tickets. With no
   `acli` or no auth both sources are `unknown` with the existing reasons,
   and nothing else is affected.

### Fixture

9. Extend `internal/dash/testdata/analysis_fixture.json` (created by gh-97;
   create it here if gh-97 has not landed) with an active sprint, a goal,
   tickets in each status category, an unassigned ticket, a ticket with no
   PR, a Done ticket whose PR is still open, and an In Progress ticket whose
   PR merged — all invented.

## Edge cases and constraints

- A ticket in several sprints (carried over): `sprints` lists all and retains
  an `in_sprint` edge to every known sprint node. The selected active sprint
  controls which membership the sprint view displays.
- Multiple active sprints on one board (parallel team sprints): each is a
  sprint node.
- Next-gen (team-managed) projects use `parent` instead of an epic link; both
  map to `parent`.
- Custom field values vary in shape (option objects, arrays, numbers);
  parsing tolerates each and treats anything unrecognised as unknown, with a
  diagnostic.
- Sprint searches are bounded to 200 tickets per sprint; beyond that the
  sprint is marked `truncated`. The returned count is not a total
  when truncated. Future sprints have metadata but no ticket search in this
  spec; recently closed sprints are not loaded.

## Out of scope

- Writing to Jira.
- Boards other than `[jira] board` (a list of boards may follow later).
- Velocity, burndown or forecasting.

## Acceptance criteria

- [ ] Parsing tests from captured, sanitized `acli` JSON cover every field in

- [ ] `[jira.fields]` overrides discovery; discovery results are cached and

- [ ] Sprint nodes carry goal and dates; sprint tickets without a PR appear

- [ ] The active sprint fixture includes an unassigned ticket; it appears in

      the configured-people-and-unassigned scope, returned count and

- [ ] A failed active-sprint ticket search leaves sprint metadata visible and

- [ ] Old `jiracache` entries still load; the statusline benchmark or timing

- [ ] Without `acli`, the dash loads with `jira` and `jira_sprints` unknown

## Delivery notes

### `acli` field support (requirement 4)

Checked on 2026-11-03 with acli 1.3.19 (1.3.40 was current). The acli
login had expired, so no request reached a Jira site. Field support comes
from acli's own client-side checks (which run before authentication),
`--help`, and Atlassian's command reference. Anything that needs a live
response is marked *unverified*.

| Field | `workitem view --fields` | `workitem search --fields` |
|---|---|---|
| `summary`, `status` (with `statusCategory`), `issuetype`, `priority`, `assignee`, `labels` | yes | yes |
| `components`, `parent`, `resolution`, `resolutiondate`, `created`, `updated` | yes, any field name is accepted (*unverified*) | no: acli refuses with "field '…' is not allowed" before any request |
| story points, sprint, team, epic link (`customfield_NNNNN`) | `*all` returns every field keyed by its ID (acli's help documents `*all`; *unverified*). Third-party notes report that naming one custom field ID fails on some acli versions. | no: refused before any request |
| field names (Jira's `names` map) | not returned; acli has no `expand` option | no |

- `workitem search` accepts only `key`, `summary`, `status`, `issuetype`,
  `priority`, `assignee`, `labels`, `description`, `reporter` and `creator`.
  It refuses `*all` and `*navigable`.
- No acli command lists a site's fields: `acli jira field` only creates,
  updates, deletes and restores fields. So no field can be discovered by
  name. The sprint field can be found by the shape of its value. Story
  points, team and the legacy epic link need `[jira.fields]`.
- `acli jira sprint list-workitems --fields` accepts custom field IDs
  before authentication. Whether it returns them, and in what JSON shape,
  is *unverified*. It could later replace the per-ticket views below.

### What the implementation does with this

- **Ticket facts.** `workitem view --fields '*all' --json` per ticket, in
  the background refresh (`_refresh-jira` and the dash `Refresher`). Every
  command that writes a ticket entry loads `~/.wgo/config.toml` first, so
  `[jira.fields]` always applies. The statusline reads only the cache. Only
  if acli refuses the field list ("not allowed") does wgo ask again for the
  system fields by name. That entry is marked partial (story points,
  sprints and team unknown, with a diagnostic) and is retried after 2
  minutes instead of the full TTL. Any other error, such as an expired
  login, costs one call. acli's site lookup runs at most once per 15
  minutes per process, and never when `jira.site` is set.
- **Sprint tickets.** `workitem search` asks only for the allowed fields,
  with `--paginate --limit 201`. Jira serves at most one page of issues per
  request, and acli may print one JSON array per page; wgo reads every page
  and keeps 200, marking the sprint truncated beyond that. That gives each
  ticket's sprint membership and a few facts. The full facts follow through
  each ticket's own `jira` refresh job, which runs only for tickets whose
  entry is not fresh. A waited-for refresh (`wgo dash --json --refresh`)
  runs those jobs as a second round, with a queue large enough for the whole
  batch. Jobs beyond any queue bound are shown as not run, not as a failure.
- **Failed searches.** Jira rejects a search that names an identity it does
  not know. When a search of several people fails, each is searched alone.
  The rest still find their tickets, the rejected identity is reported with
  its config key (`[pair] teammate_jira` or a `[[dash.people]]` entry's
  `jira`), and it is left out of the board's later sprints. A sprint whose
  search failed keeps the tickets of its last good search, shown as stale
  with the error, and the board is retried after 2 minutes.
- **Field IDs.** `[jira.fields]` comes first. Otherwise wgo uses discovery,
  cached for 7 days in `~/.wgo/cache/jira/fields.json`: by name when the
  JSON carries a `names` map (acli's does not today), otherwise only the
  sprint field, by its value. `"none"` marks a field the site does not have.
- **Shapes parsed.** Story points: a number, a numeric string or null.
  Sprint: an array of sprint objects, the legacy
  `com.atlassian.greenhopper.service.sprint.Sprint@…[id=…,…]` strings, a
  single object, or null. Team: a string, an option (`value`), an Atlassian
  team (`name` or `title`), or arrays of those. Epic link: a key string or
  an object with a key. Any other shape is unknown, with a diagnostic
  naming the field ID and its `[jira.fields]` key. A configured field that
  is missing from a ticket's full JSON is unknown without a diagnostic:
  issue types outside a field's context lack it (story points on bugs), so
  a note would stand forever even when the ID is right.
- **Diagnostics by cause.** A note never names a ticket. wgo dash shows
  each cause once, with how many tickets it affects and the first three
  keys, so a sprint of 200 tickets with one unreadable field is one line.
- **Unestimated vs unknown.** `story_points_known` marks a ticket whose
  story points field was read, so a missing `story_points` means
  unestimated only when it is set.
- **Test data.** The acli JSON in the tests is built from Jira's REST
  issue shape, which acli prints unchanged, with invented values. It was
  not captured, because the login had expired. Once acli is logged in
  again, these checks are worth repeating:
  - `acli jira workitem view <key> --fields '*all' --json`: are custom
    fields returned, and what does acli print if it refuses the list?
  - `acli jira workitem search --jql '<sprint with more than 100 tickets>'
    --json --paginate --limit 201`: are the two flags accepted together,
    does the output come as one array or one per page, and does `--limit`
    stop the pagination?
  - The error text of a search that names an unknown assignee.
  - `acli jira sprint list-workitems --sprint <id> --board <id> --fields
    <custom field> --json`.
